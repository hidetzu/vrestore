# 0018 — 局所の optical flow で実画素を運ぶのは、動きが大きく、すべての確かめを通った画素だけにする

ADR 0017（`--temporal auto`）に、画面全体の動きとは別の候補を足す。

## 決定

- `--temporal auto` で、画面全体の動き（temporal.zig）で戻せなかった画素に、局所の optical flow（`src/local_temporal.zig`、`src/flow.zig`）を試す。
  `--local-flow off` で止められる。on / off では使わない。GUI の R（1 フレームだけの復元）でも使わない
- flow: ROI の周り（ROI・おとりを含む範囲 + 24 px）だけで、ピラミッド型の Lucas–Kanade（輝度、7x7 の窓、4 段）。
  ウォーターマーク（とおとり）の画素は窓の計算に使わず、その中の flow は周りから harmonic で補う
- 次をすべて満たした画素だけを `temporal_real` にする（条件は緩めない）:
  1. 大きな局所の動き: ROI の周りの帯の輝度の変化の平均（前後 15 フレーム）≥ 3、かつ帯の flow の大きさの 90 パーセンタイルの平均（前後 45 フレーム）≥ 1.5 px/フレーム
  2. 鎖: 前後それぞれ最大 45 フレーム、一歩ごとに往復（forward-backward）のずれ ≤ 0.5 px。合わなくなったらその先はたどらない。画面の端から 8 px 以内には入らない
  3. 借りる元: ウォーターマーク（マスクで隠した画素、無ければ ROI + 8 px。ADR 0016）の外で、flow を求めた範囲の中
  4. 候補: 5 枚以上、過去と未来の両方を含み、中央値からのずれ（R/G/B の最大）≤ 8。値は中央値
  5. 実行時の疑似チェック: ROI の隣（下・上・右・左のうち画面に収まる最初の 2 か所）に同じ大きさのおとりを置き、同じ手順で戻した画素を
     実際の入力と比べる。どちらのおとりでも 100 画素以上を採り、外れ（誤差 > 32）が 0.5% 以下のフレームでだけ、本物の ROI の候補を採る
- 高い処理（flow・おとり）に入る前の関門（early gate）。どれも「試すかどうか」だけを決め、採る条件は変えない:
  - 帯の輝度の変化（前後 15 フレーム）が小さければ flow を求めない。flow の関門は前後 2 ペアだけで判断する
  - flow のペアは、関門・鎖が必要としたときにだけ求め、窓の中で使い回す
  - おとりは、まず 3 画素おきに見て、採れる数・外れの率が届く見込みが無ければ全部は見ない。1 か所が不合格なら残りは見ない
  - おとりが不合格なら、次のフレームから休む（1, 2, 4, … 最大 16 フレーム。合格で 1 に戻す）。前後 45 フレームの窓がそろわない所（動画の端）では休まない
- 局所の方式で戻した画素は、debug の可視化でシアンにする（画面全体の方式は緑）。集計に `local_flow` を出す

## 理由

- 止まったカメラの前で人・物が動くと、画面全体の動きは 0 で、画面全体の方式は何も戻せない。動く物の模様は、前後のフレームでは
  ウォーターマークの外に写っていることがあり、局所の動きで運べる（ProPainter などの flow による伝播と同じ考え方、tmp/input.md）
- 1 フレームの往復だけ・候補 1〜2 枚では外れが多い。Python の試作（実写 16 ケース、DIS の flow）で、「2 枚以上・どちらか片側」に緩めると外れが 12.5%、
  「3 枚以上・両側」では 0.4〜2.4% だった
- flow の窓がウォーターマークにかかると、止まった側に引っぱられる（ブロックの右 1 px で 9.99 px ずれ、外すと 0.18 px）
- ROI の中の flow は周りから補うので、周りの動きが混ざる（止まった背景と動く物の境目）と正しくない。そのときは候補がそろわず採らない側に倒れる。
  採った画素が本当に正しいかは、正解の無い実写ではおとりで確かめるしかない（ADR 0017 の疑似チェックを、実行時にフレームごとに行う）

## 条件を厳しくした経緯

最初の実装（3 枚・ずれ 12・往復 1 px・おとり 1 か所で 50 画素以上・外れ 1%）は、ウォーターマークの無い場所に置いた実写の疑似チェック（20 クリップ）で、
画面の端の位置で採った 3,590 画素の 11.8%、中央で 95,474 画素の 1.18% が外れだった。そのフレームのおとりは合格していた（おとりと本物の範囲では中身も動きも違う）。
上の条件に厳しくすると、左上 0 画素、中央 282 画素・外れ 0 になった（SPEC §4）。

## 採らなかったもの

- **条件を緩めて戻す量を増やす**: 試作で外れが 12.5% に増えた（上）
- **間を空けたフレームと直接 flow を取る**: 外れは少ないが、離れたフレームほど往復の確かめを通らず、戻す量が減った（試作で 0.4%）
- **学習済みの flow（RAFT など）**: 新しい実行時の依存になる。古典的な flow で足りない場面が測れてから

## 帰結

- 手持ちの実写では、この条件で本物の ROI の画素を採ることはほぼ無い（動く被写体の 16 ケースで 0 画素、疑似チェックで 282 画素）。
  試したフレームは、おとりで 100 画素を採れずに不合格になった。採れるのは、合成のように ROI と周りを覆う大きな模様が、
  前後それぞれ見える位置まで動く場面（止まった背景の上の円板で ROI の 46%、外れ 0）
- 静止カメラの前でゆっくり動く人（1 フレームに 1 px 未満）は、関門で試さないか、候補がそろわず、harmonic で埋める（利用者の判断で可）
- 横に長い ROI の中を横に動く物は、前後の両方で見える位置まで出るのに時間がかかり、両側がそろいにくい
- flow を求める分、動きの大きい区間では遅くなる（640x360・10 秒の手持ちの区間で 25 → 106 秒、early gate で 92 秒。静止カメラの区間は関門で止まり変わらない、SPEC §4）。
  残りの大半は flow のペアで、おとりが前後 45 フレームまで鎖をたどるかぎり減らせない。休みを長くして試すフレームを大きく間引くか、flow を速くするのは、測ってから
